Autonomous Multi-Agent System Architecture

A coordinated mesh of 6 sequential pipeline relay agents + 1 autonomous self-healing sub-agent executing with strict governance.

🧠 Agent 2: AI Architect

👤 Agent 3: Compliance Officer
Human-in-the-Loop Gate

Engine: Human Operator Verification Interface

Non-Negotiable Gate: AI-generated code CANNOT execute without human sign-off. Renders interactive tables, lineage flow, and collects cryptographic approval (status: approved).

🛡️ Agent 4: Sentinel Validator
Schema Gatekeeper

Pydantic R4/R4B validation (extra='forbid'). Zero tolerance: 0 errors required to pass to Agent 5. Diverts exceptions to Agent 4B.

🩹 Agent 4B: Self-Healer

Intercepts Pydantic validation errors, queries Gemini for surgical diffs, applies fixes, and re-validates cleanly with immutable audit logging.

⚡ Agent 5: Dispatcher Agent

Section 6 & 10 • Extensibility

HL7 FHIR 80/20 Pareto Principle & Zero-Data-Loss

Why the AI maps 14 core clinical attributes automatically while preserving 14 proprietary/audit columns as typed FHIR extensions.

⚖️ The Official HL7 80/20 Architectural Rule

Health Level Seven International designed FHIR around an explicit Pareto distribution:

  • The 80% (Base Core Schema): Universal clinical elements agreed upon by 80% of hospitals globally: name, gender, birthDate, identifier, telecom.
  • The 20% (Extensibility Layer): Local laws, billing systems, and database internals. HL7 forbids adding custom fields to core schemas and mandates FHIR Extensions.
Industry Analogy: Epic and Cerner use extensions for proprietary flags (http://open.epic.com/FHIR/...). US Core mandates extensions for Race, Ethnicity, and Birth Sex.

14 Core Mapped 14 memid, ssn, fullname, dob, sex, status, primarylanguage, marital, multiplebirth, IDs Direct FHIR standard: identifier[], name[], birthDate, gender, active
14 Extensions 14 lastupdate, updateid, createdate, createid, externalediting, EligibilityOfficeId, isvip, issubscriber Preserved in extension[n].valueString, valueBoolean, valueDecimal

4. Closed-Loop Re-Validation & Audit History
Re-executes apply_mapping against Sentinel Validator. Logs immutable change record in healingHistory.
💻 Surgical Code Implementation (heal.py)
def heal_mapping_config(mapping, sample, errors, api_key, model):
    # 1. Compile structured diagnostics
    prompt = f"""Failed Records: {sample}
Validation Errors: {errors}
Current Mapping: {mapping.model_dump_json()}"""

    # 2. Query Gemini for surgical repair
    healed_raw = call_gemini_repair(prompt, HEAL_SYSTEM)
    healed_cfg = MappingConfig.model_validate(healed_raw)

    # 3. Verify fix against Sentinel Validator
    res, errs = apply_mapping(healed_cfg, sample)
    assert len(errs) == 0, "Repair failed to validate"

    # 4. Record immutable audit lineage
    healed_cfg.metadata["healing_history"].append({
        "timestamp": datetime.now(timezone.utc).isoformat(),
        "repaired_errors": errors,
    })
    return healed_cfg

🔍 Incident Root Cause Dissection

During 650-record batch streaming, records #640–#650 failed with HTTP 429: Too Many Requests:

  • The Ceiling: Medplum runs RateLimiterRedis capping requests at 50,000 points/minute.
  • The Math: $639\text{ records} \times 78.3\text{ pts} = \mathbf{50,040\text{ points}}$ (breached at record #640).
  • The Failure: Client's old backoff waited only $0.5 + 1.0 + 2.0 = \mathbf{3.5\text{s}}$ total, but Medplum required 36 seconds! Retries expired prematurely.

Section 9 • Data Formats

Native Microsoft Excel OpenXML Date Ingestion

Resolving the 650-record batch quarantine caused by Excel serial day counts (39216, 18476) vs. standard CSV strings.

📄 OpenXML Serial Numbers vs. CSV Strings

Why did CSV upload succeed with 639 delivered, but Excel .xlsx failed all 650 records?

FormatInternal StorageRaw Extracted ValueResult
CSV Text string "1985-06-15" Validated 100%
Excel (.xlsx) OpenXML <c><v>39216</v></c> "39216" (Day count) Quarantined 650
The Excel Date Formula: Days elapsed since December 30, 1899:
  • 1899-12-30 + 39,216 days = 2007-05-14 (May 14, 2007)
  • 1899-12-30 + 18,476 days = 1950-08-01 (August 1, 1950)
  • 1899-12-30 + 45,000 days = 2023-03-15 (March 15, 2023)
⚙️ 3-Layer Universal Date Solution
🧠
Layer 1: Core Engine Auto-Conversion (engine.py)
normalize_fhir_datetime detects numeric strings ($1 \le n \le 100,000$), calculates base_date + timedelta(days=n), emitting valid YYYY-MM-DD.
📑
Layer 2: OpenXML Style Inspection (upload_pipeline.py)
Inspects styles.xml for date format IDs (14–22, custom yy/mm/dd), pre-converting cells during initial extraction.
💡
Layer 3: Smart UI Modal Priority (EditRecordModal.jsx)
Prioritizes exact dob column over lastupdate, offering a 1-click ✨ Convert Excel Serial Date '39216' ➔ '2007-05-14' AI action.
